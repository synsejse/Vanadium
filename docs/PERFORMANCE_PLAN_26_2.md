## Current limits

Entities (including their AI/navigation), supported block entities, scheduled callbacks,
natural spawn attempts, random/weather chunk ticks, and tracking tasks already enter
worker waves. Worlds, stages, and four colors advance sequentially. One cell executes
all of its tasks serially. Moving a method to a worker does not remove its contribution
to tick latency when the server must wait for it.

`WorkerPool` counts background helpers separately from the participating server thread.
Auto configuration can therefore request 72 helpers plus the caller on a machine exposing
72 logical CPUs, alongside C2ME, GC, and networking threads. Actual concurrency is bounded
by runnable cells in the current color. A dense base in one cell remains one task regardless
of the number of workers. The profiler measures wave execution but omits collection and
serial fallbacks; caller tail wait is not a measurement of monitor contention.

## Ranked implementation candidates

1. **Measure the serial portions and cell imbalance.** Add per-world collection/fallback
   timing, distinguish spawning from random ticking, and record bounded cell-duration
   distributions during opt-in profiles. Use JFR alongside this for CPU, allocation,
   monitors, parks, and server task-pump work outside tick callbacks. Establish dense-base,
   dispersed-player, many-mob, redstone, and exploration workloads before comparing changes.

2. **Reduce global navigation invalidation work.** `ServerLevel.sendBlockUpdated` scans
   every navigating mob after collision-shape changes, calls `shouldRecomputePath`, then
   recomputes matching paths. This occurs on whichever thread changes the block. Many
   independent edits can therefore repeat full scans and contend on navigation monitors.
   Build a conservative spatial index of navigation influence, maintaining it on path and
   entity changes. Its candidate region must cover vanilla's midpoint/remaining-node
   predicate, not just the blocks directly on the path. Preserve invalidation semantics
   before considering delayed/batched recomputation. This reduces both caller and worker work.

3. **Partition tracking preparation.** `NearbyTrackers.tick` serially detects moves,
   updates the area map, diffs every player's candidate set, and creates tasks. Initially
   snapshot stable inputs, prepare independent per-player diffs in parallel, then merge
   results by tracker so each tracker still has one writer. Preserve start/stop/data packet
   order and avoid concurrent writes to the existing identity maps/sets. Replace repeated
   full scans with dirty updates only after movement, range, passenger, and player lifecycle
   invalidation are covered. Parallel dispatch alone leaves this preparation on the caller.

4. **Parallelize spawn-state preparation.** `ServerChunkCache.tickChunks` calls
   `NaturalSpawner.createState` before dispatching chunk work. It scans entities and builds
   category counts, local caps, and potential charges serially. Partition stable entity
   inputs, accumulate locally, and reduce before spawn attempts. Avoid copying all the
   expensive work into a new serial snapshot phase. Incremental counting is a later option:
   persistence changes, entity movement/removal, and mod behavior complicate invalidation.
   Shared cap/density check-and-accounting semantics need explicit treatment; independently
   synchronized `SpawnState` methods do not make the whole spawn decision atomic.

5. **Remove specific contention after establishing state ownership.**
   - `CollectingNeighborUpdater.addAndRun` holds one per-world monitor through the entire
     recursive update drain. Independent redstone machines can serialize here. Region-owned
     update queues need explicit handling of chains crossing regions, recursion limits,
     event ordering, and conflicting mutations. Simply using thread-local queues is unsafe.
     The copy-on-write `addedThisLayer` list is also a candidate for removal once all access
     is proven to be covered by that monitor, reducing unnecessary copies without widening
     concurrency first.
   - `ItemEntityMixin` has a static merge lock across all item entities and worlds. A narrower
     design needs deterministic multi-entity locking and coordinated pickup/removal, with
     stack counts rechecked under the locks. Locking only the initiating item is insufficient.
   - `SyncAllMixin` synchronizes instance methods across shared and entity-local objects.
     Investigate shared random, path-type cache, world-border, and spawn-state contention
     individually. Never remove all synchronization as a performance experiment.
   - Random chunk ticks share `Level.random` and the plain mutable `Level.randValue` used by
     `getBlockRandomPos`. A region-owned random stream could reduce contention and eliminate
     this shared mutable position seed, but deliberately changes random sequences and needs
     a documented seeding/lifecycle policy. C2ME's world-random replacement is cancelled here.

6. **Prepare chunk packets in parallel at a stable boundary.** `MinecraftServer.tickChildren`
   calls `PlayerChunkSender.sendNextChunks` serially; packet construction reads chunk/light/
   block-entity state there. Netty transport is already asynchronous. Keep selection, quotas,
   acknowledgment state and batch ordering owned by the server; parallelize safe packet
   preparation with bounded queues and completion before conflicting world mutations, or
   use immutable snapshots. Measure snapshot cost. Block-change broadcasts are another
   candidate. The pinned C2ME no-tick-view-distance module modifies `PlayerChunkSender`
   batching, so retain its behavior. Its inspected sender mixin adjusts quota behavior;
   this inspection is not a complete transformed-runtime compatibility audit.

## Correctness prerequisites confirmed in 26.2

- Scheduled callbacks execute after `LevelTicks.tick` returns and clears its bookkeeping.
  `willTickThisTick` therefore cannot see the remaining queued callbacks as vanilla does.
  Preserve pending/executing state through worker completion without holding the scheduler
  monitor across the barrier. Merely delaying cleanup is insufficient if collection has
  already drained the pending queue.
- Serial entity rules only check roots; `tickNonPassenger` recursively calls `tickPassenger`.
  A restricted passenger can still execute inside an unrestricted vehicle's worker task.
- The block-event replacement is a deque, while vanilla uses an insertion-ordered set.
  Duplicate events are admitted. Restore ordered deduplication before parallelizing the drain.
- The plain `randValue` update and spawn check/accounting issue above remain relevant.

These are source-backed differences/exposed state, not claims that every one has produced
a reproduced gameplay failure. Existing smoke tests do not exercise all of them.

## Larger architectural direction

For more aggressive parallelism, assign simulation state to regions and give each region
ownership of tick queues, entity membership, random state, and deferred effects. Independent
regions can eventually advance without global color barriers when dependencies are resolved.
Boundary interactions need defined synchronization or ownership transfer; arbitrary modded
machines can touch distant chunks and dimensions, so spatial distance alone is insufficient.
Maintain narrow serialization points for global state and explicit support for the intended
modpack. Accepting fewer compatible mods makes this more tractable but does not remove the
need to preserve vanilla cross-region interactions.

Players also have substantial serial work: `ServerGamePacketListenerImpl.tick` calls
`ServerPlayer.doTick`, which includes base simulation, containers, inventory updates and
scoreboard/stat effects. Move player simulation only after packet ordering, region ownership,
teleports and shared containers have a design. Running whole connection ticks concurrently
would be a much larger change. Parallel worlds likewise require per-world scheduler state,
cross-dimension transfers and shared-server coordination; they mainly help when several
dimensions are busy, not when one base dominates one dimension.

## Dual-Xeon and modpack validation

Intel specifies 18 cores/36 threads per E5-2699 v3: the pair has 36 physical cores and
72 logical threads. Compare 8, 16, 24, 32 and 48 helpers, with 72 as a comparison rather
than the assumed optimum. Keep cell size fixed during that sweep, then sweep cell size.
Keep C2ME's CPU budget fixed and record it. Compare one-socket and both-socket CPU/memory
placement on the target host: remote memory costs differ under NUMA. No optimal count or
affinity is established by this review.

Use vanilla + required libraries/C2ME without Vanadium, Vanadium disabled, and Vanadium
enabled as separate baselines: disabled mode retains structural mixins and locks. Measure
tick p95/p99, throughput, allocation and lock waits under steady-state and generation loads.
Include multiplayer movement, chunk boundaries, saves/reloads and modded machine interactions.
The local Ryzen cannot establish scaling on the dual Xeon.

Keep C2ME responsible for generation/loading/lighting/IO work already covered there.
The current metadata rejects Lithium and VMP; adding either or another entity-threading mod
requires deliberate integration, not just removing a metadata conflict. Select a concrete
modpack and assign one implementation to each overlapping subsystem.
