Tasks

Minecraft 26.3, official unobfuscated names, Java 25. Versions and the C2ME release URL/checksum and Loom/JCTools versions are pinned in gradle.properties; Kotlin is pinned in build.gradle.kts and Gradle by the wrapper. Use nix-shell or nix develop and the checked-in ./gradlew. Initial dependency resolution needs network access.

Player-facing settings, JVM properties and commands are in Configuration. Contributor rules (concurrency invariants, hot-path and validation discipline) are in AGENTS.md; this page holds the commands and what they check.

Routine correctness validation is ./gradlew build runIntegration, then git diff --check. The bench* and run*Bench/runColdExplosion tasks are opt-in measurements in Gradle's benchmark group, never part of build or runIntegration.

Build and unit tests

build compiles Kotlin/Java, validates the access widener, runs JUnit 5 tests, and produces release/source jars in build/libs/. Its checkModDependencies step fails when a hand-written depends minimum in fabric.mod.json differs from the version pinned in gradle.properties (or the Java toolchain): the minima are the pins on purpose, since only the pins are built and tested, so a pin change updates the manifest in the same commit. Test reports are in build/reports/tests/test/. Kotlin warnings and all Java lint warnings fail compilation. Keep unavoidable Mixin generic casts and fastutil accessor overrides documented with local suppressions.

Build and verification configuration is separated:

  • build.gradle.kts: mod dependencies, toolchains, resources and release packaging.
  • buildSrc/src/main/kotlin/vanadium.verification.gradle.kts: unit tests, live fixtures and benchmarks.
  • buildSrc/src/main/kotlin/com/synsenetwork/vanadium/gradle/: typed download/launch actions and fixture definitions. LiveLaunch resolves each fixture's launch values and expected outputs from its -P properties in one place, and only when that fixture's run executes: a malformed mixed.*, cold.* or bench.* value fails that run before launch and never build or another fixture.

Production packages follow responsibilities: tick/ owns wave scheduling and dispatch; stage/ owns what each stage queues; navigation/ owns path invalidation and path-type caching; spawning/ owns counting; diagnostics/ owns profiling, JFR events, the slow-wave watchdog, the crash-report section and capture summaries. commands/VanadiumCommand.kt registers the command tree and calls those components. Corresponding unit tests live in the same packages; live Fabric scenarios remain in integration/. PreparationKind labels independent jobs, and PerformanceResults publishes their captures. Package moves change class names in stack traces; the vanadium.* JFR event names, enum labels, JSON fields and command paths remain stable.

The build-logic tests (./gradlew -p buildSrc check) validate verified downloads and rejection of corrupt artifacts without accessing the network, fixture property parsing, launch values and output verification.

Unit tests inspect vanilla bindings without booting Minecraft or applying mixins. They are necessary but insufficient to validate a port.

Live server integration tests

Keep the deterministic concurrency, mixin-binding and collection-contract tests: the current unit suite takes seconds, and removing them would not shorten long benchmark campaigns.

Read the Minecraft EULA. If accepted, create .vanadium/eula.txt containing eula=true, or copy your existing accepted file. Then run:

Shell 
./gradlew prepareRuntimeMods
./gradlew runIntegration
./gradlew runIntegration -Plive.jfr=true

prepareRuntimeMods downloads and SHA-512-verifies the pinned C2ME and Lithium releases into .vanadium/mods/. Neither is flattened into Loom's development runtime classpath: live runs copy both release jars into the run's mods/. Vanadium compiles against the verified Lithium jar (compileOnly), and unit tests use it to check mixin bindings, including injections into methods Lithium merges. Fabric API, Fabric Language Kotlin and Cloth Config are normal Gradle dependencies. ./gradlew setupRuntimeMods also installs the verified jars into the interactive run's mods/; runClient and runServer run this setup automatically. A conflicting C2ME/Lithium version or modified pinned file stops setup with its path; other mods are kept. Neither task flattens C2ME's nested jars into the development classpath.

runIntegration builds a test-only Fabric mod from src/test/kotlin/, starts a dedicated server through Loom, and runs the live assertions in-process. It also executes the mod's status command through the server dispatcher. The fixture advances the ticked regression scenarios at uncapped speed, allows two cleanup ticks, flush-saves, requests normal shutdown, and writes a completion marker only after the server stops. The Gradle task checks that marker and has a five-minute timeout. There is no nested Gradle process, RCON client, Python launcher, or process-scanning cleanup. Loom finalizes launch paths before task execution, so live runs require configuration caching to be off (the repository default). Use --no-configuration-cache if you enable it globally; normal Gradle compilation/test up-to-date checks remain available.

-Plive.ticks=500 sets the maximum ticks for the scenario sequence (the default is 500, not 500 ticks per scenario). Checks stop early when complete; running out of ticks fails with the current step's name. -Plive.sprint=false restores normal tick pacing for debugging. Sprinting uses vanilla's tick sprint: it keeps real ticks, packet handling and stage barriers, and only removes the 20 TPS pacing. Async chunk/ticket readiness waits temporarily restore 20 TPS so background generation can finish without exhausting a tick budget in milliseconds. These waits end when ready, and count toward the same budget. Startup checks and chunk generation still take real time; the five-minute process timeout also catches a stalled tick. LIVE_CHECK_DONE lines report each startup check's elapsed milliseconds, and LIVE_TICKS_DONE reports the actual tick count and duration. LIVE_STEP_DONE and LIVE_PHASE_DONE lines give the ticks (paced ones separately) and wall time of each ticked step and of each fixture's steps together; LIVE_SERVER_STARTED, LIVE_CHECKS_DONE, LIVE_SAVE_DONE and LIVE_STOP_DONE time JVM startup, all startup checks, the final save and the shutdown.

Each invocation uses a fresh .vanadium/runs/integration-UUID/ directory with a loopback-only port, seed 12345, flat world, four helpers, isolation two, C2ME parallelism four, and a fixed 2 GiB G1 heap. Personal run/ state is never copied over or deleted. Worlds, logs/latest.log and failure evidence stay in that directory. Test classes and the completion helper are packaged only in build/test-mods/integration-checks.jar, never the release jar.

The live suite covers two-player joins, chunk delivery and acknowledgements, entity tracking, movement across a chunk boundary, a client block-break request observed by the other player, disconnect cleanup, block update packets, dirty-chunk notifications, loaded chunk publication/replacement/unload, real loads under the per-chunk load locks, disabled mode, scheduled ticks, what the spawning and block-entity stages queue or run inline with each of their options off, passengers, events, navigation invalidation, pathfinding parity, inside-block and line-of-sight parity, tracking diffs, spawn-count reduction, item conservation and chunk packet encoding/sending. The JFR option records monitor/park events at 100 µs plus execution/allocation samples into the run's live.jfr.

live/TestPlayer.kt (shared by the live fixtures) provides reusable real ServerPlayer instances joined through PlayerList.placeNewPlayer and ticked through ServerConnectionListener. Only the transport is mocked: packets are recorded, client actions use the real packet handlers, and teleport/chunk/keepalive acknowledgements arrive on the next connection tick. Each server tick drives one simulated client tick, including the tick-end packet required by movement validation. This does not test login authentication, socket transport, wire codecs or rendering. Tests must close each player on the server thread.

Manual coverage is still needed for real clients, portals/dimensions, exploration and concurrent cold loads, interacting redstone/fluid machines, custom environment-driven spawn costs, modpacks and integrated-server reopen. A passing build/live fixture is not a general world-safety or performance claim.

Benchmarks and profiling

Shell 
./gradlew runFeatureBench
./gradlew runFeatureBench -Pbench.filter='spawn-.*' -Pbench.rounds=2 -Pbench.scale=0.1 -Pbench.jfr=false
./gradlew runMixedBench -Pmixed.mode=enabled
./gradlew runMixedBench -Pmixed.mode=serial
./gradlew runColdExplosion -Pcold.arm=sham
./gradlew runColdExplosion -Pcold.arm=warmup
Run one live server at a time: the live fixtures and runIntegration must never overlap.

runFeatureBench uses another fresh isolated server and a test-only mod. It runs paired on/off workloads with warmup and alternating order, writing CSV and optional per-arm JFR files under feature-bench/ in that server directory, then ticks/saves/shuts down normally. Defaults are four helpers, isolation two, 12 paired rounds, scale 1 and JFR enabled. bench.workers, bench.rounds, bench.scale, bench.filter and bench.jfr are Gradle properties; bench.rounds (0–1,000,000) and bench.jfr (true/false) are validated before launch. bench.filter is a regular expression over whole case names; empty runs every case, and one that matches no case fails the run itself, listing the case names. After the run, the task checks environment.txt, a samples.csv with at least one selected case's rows (header plus two per round) and, with JFR, non-empty *-off.jfr/*-on.jfr recordings. Reduced scale/rounds only check the harness; they are not performance evidence. For independent JVM samples, invoke the task again; each run gets a new world and JVM.

runMixedBench is a manual whole-server benchmark: real players over the mocked transport walking around player bases with furnaces, hoppers, redstone, farms, animals and villagers on generated terrain with natural spawning, measured in fixed-tick windows. It runs one mode per invocation in a fresh .vanadium/runs/mixedBench-UUID/ directory and takes several minutes; see Profiling for the workload, mixed.* properties, outputs and how to compare modes. It is never part of build or runIntegration.

runColdExplosion is a manual fixture for the first explosion in a fresh JVM: ordinary creeper blasts in identical arenas on a fixed tick schedule, with one arm per invocation (sham, warmup or the load-only load control). See Profiling for the schedule, outputs and how to read the arms. It is never part of build or runIntegration.

For whole-server measurements use /vanadium benchmark, /vanadium profile, and the JDK's jcmd/jfr tools; see Profiling. Old exploratory harnesses and 26.2 reports have been removed; current chart evidence is in Performance. Record hardware, worker/isolation/C2ME settings, heap, flags, mod versions and workload whenever publishing new measurements.

Interactive development

./gradlew runServer and runClient automatically install verified C2ME and Lithium into run/mods/ before launch. To install them without starting the game (including before an IDE launch), use ./gradlew setupRuntimeMods. -PvanadiumRunDir=/absolute/path selects a separate interactive client/server directory for both setup and launch. Start the development client with:

Shell 
nix-shell --run './gradlew runClient'

Or enter nix-shell first, then run ./gradlew runClient. nix develop -c ./gradlew runClient uses the same shell definition in nix/shell.nix; both entry points use the nixpkgs version pinned by flake.lock. A separate Nix channel is not needed. The shell supplies Java 25, JDK diagnostic tools, and Linux graphics/display/audio libraries. Graphical clients still use the host display and GPU driver; launch from your desktop session.

Do not delete live Gradle cache locks if IDE imports contend with the CLI; let the other operation finish instead.
