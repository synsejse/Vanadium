## Wave scheduling and the caller-participating pool

<Lead>
  Rather than splitting a world into independent servers, Vanadium keeps one world and executes each of the six vanilla
  tick stages as a parallel wave. The calling server thread claims tasks right alongside the workers so no core sits
  idle waiting on a barrier. Full invariants live in [Architecture](architecture#planning-and-execution).
</Lead>

<Compare>

<Side tone="vanilla" label="Vanilla">
<Term>Single-lane loop</Term>

One thread walks all six stages in order. C2ME parallelizes chunk I/O and generation, and Lithium speeds up individual checks, but simulation ticks still execute one task at a time.

</Side>

<Side tone="vanadium" label="Vanadium">
<Term>Sized waves with tree fan-out wakeups</Term>

- **Work-based sizing:** Estimates participant count as `sqrt(W / c)` (`c = 2 µs`) and caps flat waves by the expected longest task so extra threads do not spin through the tail.
- **Inline fast path:** Tiny waves run directly on the server thread with zero wake-up cost.
- **Fan-out waking:** The caller unparks at most two workers; each arriving worker unparks the next indices from a shared wake cursor.

</Side>

</Compare>

## Flat entity wave and ownership locking

<Lead>
  Geographic region locking fails as soon as hundreds of mobs gather in one trading hall, farm, or combat arena:
  everything falls into one conflict clique and reverts to one thread. Vanadium ticks all entities in a single flat wave
  and replaces spatial distance with per-entity ownership ([protocol details](architecture#flat-entity-wave)).
</Lead>

<Compare>

<Side tone="vanilla" label="Vanilla">
<Term>Implicit single-thread safety</Term>

Every entity freely reads and mutates neighboring entities (push velocity, combat damage, item stack merging, breeding). Pushing allocates a fresh `Vec3` on every contact.

</Side>

<Side tone="vanadium" label="Vanadium">
<Term>Own yourself; scope only foreign writes</Term>

- **Self-ownership (`OwnerLocks`):** A tick holds its own vehicle tree's lock from start to finish, so normal self-mutations take no extra locks.
- **Push inbox (`ImpulseSlot`):** Pushes add three doubles into a lock-free spin-guarded slot with zero `Vec3` allocation and drain at the target's tick or post-wave.
- **Foreign scopes (`Interactions`):** Writing to another entity releases the caller's own lock first, then acquires the target's lock, breaking A/B deadlock cycles.
- **Pairwise scopes (`enterPair`):** Item merges, XP merges, breeding, and gossip lock both entities in ID order and recheck state inside.
- **Cache locality (`WaveHomes`):** Spread-out waves pin each entity slice to a home worker, cutting cross-socket cache transfers roughly 5×.

</Side>

</Compare>

## Adaptive regions and dual wave policies

<Lead>
  Spawning, random chunk ticks, block entities, and scheduled block ticks touch neighboring chunks. `RegionGrid`
  partitions active chunks into bounding boxes using prefix-sum quadtree splits and guarantees that no two active
  regions within `isolation` chunks (Chebyshev distance) overlap.
</Lead>

<Compare>

<Side tone="vanilla" label="Vanilla">
<Term>Whole world on one thread</Term>

Every hopper, piston, crop tick, and spawn attempt executes sequentially, even when bases sit thousands of blocks apart.

</Side>

<Side tone="vanadium" label="Vanadium">
<Term>Quadtree hotspots plus two specialized schedulers</Term>

- **Plan reuse (`RegionGrid`):** Splits dense areas toward ~25 µs per region, merges quiet tiles, and reuses stable plans for up to 20 waves.
- **Heavy work (`ClaimWave`, ≥100 µs avg):** Dynamic claiming with immediate `NO_PENDING` exit, 30 µs spin before parking, and selective unparking of only the freed neighbor count (**−94.2%** spin samples).
- **Cheap work (`DataflowWave`):** Graph-colored atomic dependency counters unlock regions as lower-colored conflicts finish with no global color barrier; kept pure-spin to avoid futex wake latency on 20–50 µs regions.

</Side>

</Compare>

<span id="crowdgrid"></span>

## CrowdGrid spatial prefilter for dense sections

<Lead>
  Entity push checks query every entity whose bounding box intersects the mob's box. In a dense chunk section with 100
  mobs, scanning the section linearly performs 10,000 bounding-box reads per tick across moving entities on other cores.
</Lead>

<Compare>

<Side tone="vanilla" label="Vanilla">
<Term>Linear scan per 16×16×16 section</Term>

Every box query iterates the entire section storage and allocates a per-query section lambda, touching distant entities on the opposite side of the chunk.

</Side>

<Side tone="vanadium" label="Vanadium">
<Term>Lock-free 2×4×2 cells above 24 entities</Term>

- **Wait-free 1-cell path:** Queries inside a single 2×4×2 cell do one volatile array load: zero locks, zero sequence retries, zero scratch memory.
- **Zero-scratch 2-cell merge:** Overlapping two cells merges two pre-sorted immutable arrays inline.
- **Lock-free moves:** Moving entities CAS into new cells before updating their box, opening the sequence counter only during old-cell deletion.
- **Vanilla-exact output:** Candidates are re-tested on live boxes and emitted in exact section list order.

</Side>

</Compare>

## Zero-allocation inside-block traversal and line of sight

<Lead>
  At high worker counts, per-tick object churn saturates memory bandwidth and forces frequent G1 GC cycles. In vanilla,
  `Entity.checkInsideBlocks` and `LivingEntity.hasLineOfSight` are two of the largest allocators in combat; Vanadium
  runs both in primitive registers with local section caching.
</Lead>

<Compare>

<Side tone="vanilla" label="Vanilla">
<Term>Throwaway objects on every check</Term>

- **`checkInsideBlocks`:** Allocates a `LongOpenHashSet` and block traversal helpers even when standing still in air.
- **`hasLineOfSight`:** Allocates two `Vec3`s, a `ClipContext`, an `EntityCollisionContext`, a `BlockHitFactory` lambda, and a `BlockHitResult` for every sight ray.

</Side>

<Side tone="vanadium" label="Vanadium">
<Term>Primitive registers, air skipping, and TickThread scratch</Term>

- **`InsideBlockFastPath`:** Stationary and single-box movements allocate 0 bytes and skip air sections directly; swept block crossings reuse a padded open-addressed table on `TickThread.insideBlockScratch` while keeping vanilla's exact 16-step order.
- **`LineOfSightFastPath`:** Exact primitive DDA raycast with bit-exact `clipsFullCube` for `Shapes.block()`; allocates `CollisionContext` and `Vec3` lazily only on partial shapes (fences, slabs, stairs).

</Side>

</Compare>

## Exact ground pathfinding and pooled search nodes

<Lead>
  In combat waves, roughly 95% of the slowest tick is a single mob executing `PathFinder.findPath`. Vanadium keeps path
  results bit-for-bit vanilla while moving all per-search scratch state onto `TickThread.walkScratch` and pooling search
  `Node` instances.
</Lead>

<Compare>

<Side tone="vanilla" label="Vanilla">
<Term>Per-search Node churn and shared cache reads</Term>

- Allocates a new `Node` per explored block inside `NodeEvaluator.nodes`.
- Reads a shared world `PathTypeCache` and Fabric's `LandPathTypeRegistry` map on every cell.
- Reconstructs paths with streams, target iterators, and quadratic list operations.

</Side>

<Side tone="vanadium" label="Vanadium">
<Term>O(1) generation tables and winner-only cloning</Term>

- **`TickThread.walkScratch`:** Cache-line-padded scratch workspace holding generation-stamped spatial caches, a lazy malus table, and an open-addressed primitive `Node` table (initial 2,048 slots) backed by a reusable pool (capped at 4,096).
- **Zero escaping pooled nodes:** Active only during `PathFinder.findPath` when `!captureDebug`; clones only the ~5–25 winning path nodes before `done()` releases the pool.
- **Fast block classification:** Reads Lithium section block flags directly from `PathNavigationRegion`, keeps global path-type slots in lock-free atomic longs (`PathTypeSlots`), and filters invalidations via `NavigationIndex`.

</Side>

</Compare>

## Lock-free chunk access, spawning, and per-thread world state

<Lead>
  At 36 workers, any remaining shared monitor becomes a serial bottleneck. JFR profiles of `mixedBench` revealed 125
  seconds of worker wait time piled onto a single C2ME `ItemHolder` lock during natural spawning structure lookups.
</Lead>

<Compare>

<Side tone="vanilla" label="Before">
<Term>Status lookups and shared world monitors</Term>

- **Structure lookups:** `ParallelChunkCache` only returned lock-free hits for `ChunkStatus.FULL`, sending every `STRUCTURE_STARTS` and `STRUCTURE_REFERENCES` lookup straight into C2ME's synchronized `ItemHolder`.
- **Spawning &amp; randoms:** Contended locks on `SpawnState`, `LocalMobCapCalculator`, `Level.random`, `Level.randValue`, and `CollectingNeighborUpdater`.

</Side>

<Side tone="vanadium" label="Vanadium">
<Term>Wait-free status reads and TickThread-owned state</Term>

- **`ParallelChunkCache`:** Published full chunks in `NonBlockingHashMapLong` satisfy every `ChunkStatus` lock-free; border proto-chunks outside loaded chunks cache per spawning wave (`beginStructureWave` / `endStructureWave`).
- **Safe server-thread handoff:** Unloaded chunk misses never block workers waiting on the server thread: deferrable tasks unwind via `runDeferrable` and non-deferrable lookups use `callOnWaveCaller`.
- **Lock-free spawning &amp; world state:** `ConcurrentMobCategoryCounts`, lazy mob counting when `spawn_mobs` is false, per-thread `PerThreadRandom` / `randValue` / `CollectingNeighborUpdater`, scratch-sorted `StableDistance` sensors, and `AreaMap` symmetric-difference tracking.

</Side>

</Compare>

## Measured performance and tuning summary

<Lead>
  At the default 36 workers on a dual Xeon E5-2699 v3 (36 cores, 72 threads), Vanadium ran these worlds 9–14× faster
  than the same server with Lithium alone. [Performance](performance) has the full sweep, the JVM flags that add 12–65%
  on top, and how it was measured.
</Lead>

| World                        | Lithium alone | Vanadium, 36 workers |                        Speed-up |
| ---------------------------- | ------------: | -------------------: | ------------------------------: |
| Spread out: 4,096 zombies    |      25.5 TPS |              367 TPS | <span class="gain">14.4×</span> |
| Crowded base: 700 mobs       |       206 TPS |            1,887 TPS |  <span class="gain">9.1×</span> |
| Combat: 600 mobs in an arena |      27.9 TPS |              298 TPS | <span class="gain">10.7×</span> |

TPS here is uncapped processing capacity: a normal server still ticks at 20 TPS and uses the headroom to stay there
under load.

<TuningList>

<TuningItem>
<Term>Keep `workers = 0` first</Term>

Resolves to `min(physical cores, logical CPUs − 1)`, leaving headroom for the server thread, C2ME, and GC. Matching logical SMT threads oversubscribes the host and drops throughput.

</TuningItem>

<TuningItem>
<Term>Pick `idleWorkers` for your host</Term>

`lean` (default) spins nothing between ticks for the least idle CPU; `balanced` spins only the server thread; `hot` keeps workers warm for lowest 20-TPS latency.

</TuningItem>

<TuningItem>
<Term>Inspect and isolate mods</Term>

Use `/vanadium status` and `/vanadium benchmark` to verify your hardware. Route custom modded entities or block entities with shared mutable state via [`serialEntityTypes`](configuration#serial-type-rules).

</TuningItem>

</TuningList>
