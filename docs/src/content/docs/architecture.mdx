## Ownership and stages

| Package              | Responsibility                                                                                                                                                                              |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `tick`               | Adaptive planning, stage scheduling, wave execution and the worker pool.                                                                                                                    |
| `stage`              | What each stage queues: one owner per level and stage (`EntityStage`, `ChunkStage`, `BlockEntityStage`, `ScheduledTickStage`).                                                              |
| `entity`             | Entity section index, crowded-section cell grids (`CrowdGrid`), and allocation-free `InsideBlockFastPath` / `LineOfSightFastPath`.                                                          |
| `concurrent`         | Entity ownership (`Interactions`, `OwnerLocks`, `ImpulseSlot`), POI claims, striped locks, per-thread world random streams, random-tick LCG, and scratch-sorted `StableDistance`.           |
| `chunk`              | Loaded-full-chunk publication, spawning-wave structure cache, server-thread load locks, packet preparation.                                                                                 |
| `tracking`           | Nearby-player ranges and tracker diffs.                                                                                                                                                     |
| `navigation`         | Navigation invalidation index, path-type cache and exact pathfinding fast paths with pooled nodes.                                                                                          |
| `spawning`           | Mob counting, lazy count state and lock-free category counts (`ConcurrentMobCategoryCounts`).                                                                                               |
| `diagnostics`        | Tick profiles, JFR events, wave watchdog, crash-report section, benchmarks, summaries and result files.                                                                                     |
| `collections`        | Fastutil-compatible adapters over JDK/JCTools collections.                                                                                                                                  |
| `compat`             | Lithium's section-storage replacement; C2ME and Lithium mixin cancellation (Java).                                                                                                          |
| `commands`, `config` | Brigadier commands, TOML configuration, live options, serial-type rules and JVM properties.                                                                                                 |
| `mixin`              | Java integration with vanilla, C2ME and Lithium, each mixin in its target class's official package (`mixin/server/level/ServerLevelMixin`); Lithium-class mixins in `mixin/compat/lithium`. |

[AGENTS.md](https://github.com/synsejse/Vanadium/blob/dev/AGENTS.md#source-map) maps the same packages to source paths and states which classes must stay Java.

`Vanadium` creates fresh scheduling state on server start and closes diagnostics and the worker pool after the last wave on shutdown. Chunk caches own their maintenance executors; load-lock tables own no threads. Integrated-server reopen must create a new lifecycle.

| Stage                            | Collection and completion boundary                                                           |
| -------------------------------- | -------------------------------------------------------------------------------------------- |
| Scheduled block/fluid ticks      | Collect under the `LevelTicks` monitor, claim lock-free and dispatch after releasing it.     |
| Spawning/thunder                 | Complete before the separate block-ticking chunk pass.                                       |
| Random/precipitation chunk ticks | Complete before custom spawners and broadcasts.                                              |
| Tracking                         | Prepare visibility diffs, then complete tracker callbacks.                                   |
| Entities                         | Vanilla's complete per-entity body as one flat wave; finish before block-entity bookkeeping. |
| Block entities                   | Queue supported tickers; finish before clearing the ticking flag.                            |

Entities are the exception to region scheduling: see [Flat entity wave](#flat-entity-wave).

Each stage's collection lives in one Kotlin owner, created with the vanilla object that owns the stage: `EntityStage` per entity tick list, `ChunkStage` (spawning and chunk ticks) per chunk cache, and `BlockEntityStage` per server level. `ScheduledTickStage` pools reusable `TickTask`s, while `LevelTicksMixin` replaces `LevelTicks`'s container maps with concurrent maps, holds the wave's due ticks and atomic claim states, and serves `willTickThisTick` from a lazy immutable wave index without taking the `LevelTicks` monitor. The mixins only forward vanilla's calls to them; the owners decide what runs inline, what is queued and what falls back to vanilla.

Disabled stages retain serial fallbacks. Structural synchronization and loaded-chunk indexing remain installed even with `enabled=false`. Projectiles, entities in portals and configured exact-ID exceptions ([serial type rules](configuration#serial-type-rules)) tick serially. A serial passenger routes its whole vehicle tree through the serial path.

Block entities also tick serially, on the server thread before the wave, while a neighbouring chunk of theirs is still loading (`BlockEntityStage.ready`). Vanilla ticks them once their chunk's ticket level allows block ticking, before its ticking future (which needs every neighbour FULL) completes, and a tick may read past the chunk's edge: `BlockEntity.setChanged` notifies comparators up to two blocks out through a solid block, unchecked. On a worker that read would wait for the server thread to load the neighbour mid-wave. Random ticks, scheduled ticks and entities already wait for those futures, so only block entities need this. Reads farther than 16 blocks (a spawner with a custom spawn range) can still reach a chunk that is not FULL; they keep the mid-wave fallback in `ParallelChunkCache`.

## Planning and execution

Entity, chunk and block-entity collection reuse their task objects across ticks instead of rebuilding closures on the server thread. `PersistentTickTasks` holds one task per entity in the tick list, in arrival order: the tick list reports adds and removes (from any thread, also mid-wave) and they apply at the next dispatch, so an entity added during a tick first ticks next tick, as with vanilla's snapshot. Serial classification is cached per entity: its type rules are recomputed when the configured rules change (compared by identity), its portal and passenger part when portal entry or a mount is reported for it or a passenger, and every tick for entities that are serial only through that part. `ChunkStage` pools `ThunderTask` and `SpawnTask` instances and caches the entity-ticking chunk positions until the simulation-level map's write version changes; each task resolves its holder and ticking chunk when it runs. `BlockEntityStage` dispatches `LevelChunk.RebindableTickingBlockEntityWrapper` directly as a `Runnable` (`BlockEntityTaskAccess`) and caches each wrapper's serial-rule match against the config's rules key. Workers never mutate stage queues.

`RegionGrid` records tasks per chunk, using floor-correct coordinates and dense 16×16 tiles. Prefix sums guide quadtree splits: the task target is the larger of a share of work (`tasks / (participants × 4)`) and approximately 25 µs of measured region work. Hotspots split; quiet or cheap areas stay merged. A region is its chunks' bounding box; tasks within it run serially in enqueue order.

Boxes within `isolation` chunks of each other in Chebyshev distance conflict. Conflict lists are symmetric and the greedy colouring is proper. This safety distance does not depend on region shape or worker count. Stable plans are reused for up to 20 waves while membership, task-count drift and estimated cost remain within their bounds. New active chunks, changed participants/isolation or expired plans trigger rebuilding.

Both policies implement `RegionWave`:

- **`ClaimWave`** dynamically claims heavy regions (estimated average ≥100 µs). Volatile `PENDING`/`TRYING`/`RUNNING`/`DONE` states and index-ordered claim resolution prevent conflicting work from overlapping. Participants exit early on `NO_PENDING`, spin 30 µs before parking on per-participant waiter slots (serving caller chunk requests and preserving the caller's interrupt flag), and selectively unpark only the count of newly freed neighbors.
- **`DataflowWave`** handles cheaper work. A region becomes ready after all lower-coloured conflicts finish. Atomic dependency counters and ready slots avoid repeated scanning, and it stays pure-spin to avoid futex wake latency on short 20–50 µs regions.

Both complete the whole wave before propagating task failures. There are no global barriers between colours, but every stage has a full completion barrier. Relative order between conflicting regions may change between ticks.

`WorkerPool` publishes one `WorkBatch` per wave. Its metadata is fixed before publication and never changes: the task list, the saved task count, participants, chunk size and, for a homed wave (`WaveHomes`, the entity wave below), the claim cells copied from the caller's layout. Its progress is mutable and atomic: the claim cursor or cells, the remaining-task counter, the wake cursor, the first failure, the busy time and the waiter's parked flag. Both helpers and the calling server thread claim work, in list order through the cursor or home by home. One-task waves run inline. Helpers spin before parking; the caller spins then parks for the tail (under pressure through tails of up to 10 ms, [below](#idle-spinning)). Late helpers use the saved task count, never a list that the caller has cleared. Interruption restores the caller's flag only after all work finishes. Never hold a monitor needed by workers while joining a wave.

Waking fans out. A worker sets its bit in a parked bitmap before its last look for a new batch; the caller reads the bits of the wave's helpers after publishing, and only when one of them may be parked does it unpark at most two of them. Each helper that joins a waking batch first takes further helper indices from the batch's wake cursor and unparks those workers, so wake-ups spread over the threads that are already awake instead of queueing on the server thread. Each index is taken once by a thread that has seen the batch, which keeps the per-worker Dekker pairing (publish, then read `parked`) whoever does the waking.

### Wave sizing

`TickScheduler` sizes every wave by its estimated work W: about `sqrt(W / c)` participants, where c (`vanadium.participantCostNanos`, 2 µs) is what involving one more thread costs. Region stages estimate W from `RegionGrid` (bounded by the conflict graph's clique cover); flat and preparation waves from the busy time `runWave` reports. Unmeasured waves use every worker; waves too small for a second thread run inline. A flat wave also knows its expected longest task L (the entity wave's longest group, smoothed: up a tenth, down half per wave). It cannot end before L does, so it gets no more than `1 + (W − L) / (0.8 L)` threads (`vanadium.criticalPathShare`, 0.8; 0 disables): the others finish the rest within 80% of L. In a 600-mob fight at 36 workers that is ~29 participants instead of 37; more would only spin through the tail. Both are measurement inputs ([JVM properties](configuration#jvm-properties)).

### Idle spinning

Idle spinning follows the tick (`SpinPolicy`). Under pressure (sprinting, or the next tick due within 2 ms of the end of this one) workers spin 2 ms through every gap. With slack they spin 500 µs between waves of a tick; what happens between ticks is the `idleWorkers` option (`IdleWorkers`):

- **`balanced`** parks workers when the tick ends, and the server thread spins through its wait for the next tick (`ServerSpin`, below).
- **`hot`** keeps workers spinning (50 ms between waves, and through the gap to 1 ms past the next tick's due time), and the server thread spins through the whole gap.
- **`lean`** parks workers when the tick ends, and the server thread sleeps until the next tick.

In every mode the next tick's start wakes the workers the previous tick used, so they are spinning by its first wave. A tick that ran nothing in parallel (an idle server) keeps nobody spinning, and a server paused when empty (`pause-when-empty-seconds`) fires no tick events at all. A `/tick freeze` server (between `/tick step`s) ticks its entities serially, as vanilla does: only players and vehicles carrying one tick, so its entity stage wakes nobody. Tracking still runs, as vanilla's does, and only counts as parallel when it has enough work to spread. Tick events are the only input: tests and benchmarks without them spin 2 ms. The caller's own two wake-ups per fan-out, the tick-start wake and the 200 µs caller spin floor are fixed; tests and `benchWorkerPool` pass other values to the constructors. `vanadium.workerSlackSpinMicros` (500 µs) sets the spin between waves with slack, for measurements ([JVM properties](configuration#jvm-properties)).

The wave's caller (the server thread) waits for the tail on its own processor, and its wake-up delays the tick itself. Under pressure it spins through tails of up to 10 ms (`vanadium.callerPressureSpinMicros`) before parking; with slack it spins as long as an idle worker would (at least 200 µs). The other way round does not work: shorter worker spins (10 or 100 µs fixed) halved sprint TPS in a 600-mob fight, and the longest entity tick itself took twice as long while the others parked and woke.

**Server spin.** At 20 TPS on the test VM a tick after a long sleep can take twice as long as the same tick under `/tick sprint`; see [Performance](performance#idle-workers-at-20-tps). `END_SERVER_TICK` arms `ServerSpin` with the next tick's due time and the mode's window. The `MinecraftServer.waitForTasks` mixin parks only until the window opens (at once, for a whole-gap window), then spins 50 µs slices and returns to vanilla's `managedBlock` loop, which polls tasks between slices exactly as before (vanilla's other waits poll every 100 µs). It spins only while the wait is for exactly the armed tick, so a wait that no tick event preceded (a paused server between its loop iterations, startup, shutdown) never spins. Spin slices are not counted as idle time in vanilla's tick-time debug samples.

## Flat entity wave

Regions cannot help where work is packed together: a base or a mob farm is one clique of conflicting regions, and its entities would tick serially while the other workers wait. The `ENTITY` stage therefore has no regions and no isolation: every entity tick is one task in a single wave, wherever it is. Other stages keep region scheduling.

What made this safe before was distance; now it is ownership (`Interactions`, `OwnerLocks`):

- A tick owns its vehicle tree: it holds that root entity's lock from start to end. Everything it writes to itself needs nothing else.
- Reads of other entities and of blocks take no lock, exactly as between regions. Sorts by distance snapshot positions first into precomputed scratch arrays (`StableDistance`), because entities move while they are being sorted.
- A push, the one thing crowded entities do to each other every tick, goes to the target's lock-free 3-double inbox (`ImpulseSlot`, zero `Vec3` allocation) and never waits; the target applies it at the start of its tick. Targets that had already ticked, or do not tick, are listed per thread and applied before the wave returns: a few on the server thread, many as a short wave in which each target is owned as in its own tick.
- An entity's section changes only when its position crosses a section boundary. Position writes within a section (nearly all) take no lock; a crossing holds the old and new section's stripes (spinning briefly before parking), so an add cannot race a same-section removal into an orphaned section. Only the entity's owner writes its position, so its unlocked section key is current.
- Any other write to another tree is a foreign write. Mixins at the mutation points open a scope: the tick releases its own lock and takes the target's, so the write waits for the target's own tick, and for nothing else: writes to different entities do not wait for each other. Releasing first keeps two entities that write to each other from deadlocking; the tick is open to foreign writes while it is in the scope, at a point where it was calling out, and a write back to itself in there takes its own lock again. The generic points are velocity, position, removal, synced data and brain memories; damage, effects and mounting are scoped as whole operations.
- Operations that two entities start on each other in the same tick take both locks in id order (a pair scope) and recheck their condition inside, so the second sees what the first did: two stacks merging, two orbs merging, a mob taking an item, two parents breeding (one birth), villagers gossiping.
- Block changes, explosions and vibration delivery from entity ticks are shared writes: they run one at a time on a shared lock, then follow the same per-chunk and neighbour-update synchronization as region work. Hoppers and beehives serialize the items and bees that enter them.
- Entities whose ticks mostly write to others run serially before the wave, like projectiles: TNT, container and TNT minecarts, the dragon, the wither, end crystals, lightning, effect clouds, evoker fangs, copper golems and wardens.

A scope nested in another (damage whose side effects reach a third entity) holds one lock while waiting for the next, so two such writers can wait on each other. A waiter follows the chain of holders and what each waits for; if it leads back to itself it proceeds without that lock, and counts it. Locks outside the protocol are invisible to that check, so every wait is also bounded (100 ms, `vanadium.interactionTimeoutMillis`). Either way one write runs unprotected instead of stalling the tick, and is reported. `Interactions` counts foreign writes by what they changed (`Interactions.Write`; `-Dvanadium.interactionLogWaves=N` logs them). The catalogue of whole operations is vanilla's; a mod's own pairwise logic is covered only by the generic points.

Wave order is a matter of balance only. A wave ends with its longest ticks, and in a crowd those are sporadic: in a 600-mob fight a villager tick runs 1.5–3.5 ms (twenty times its usual tick) about once every 40 ticks, unpredictably for the entity but steadily for its type. Wave tasks therefore persist in groups (`PersistentTickTasks`): entity types run in order of their costliest member (per wave, the largest per-entity time among the type's groups, smoothed), not their mean, so the type with the long ticks starts first even when another type costs as much on average. In that fight about 95% of the longest tick of each wave is one `PathFinder.findPath` call that ends without reaching its target (a different villager each tick), and the wave ends just after it. Each type runs in tick-list order, in groups of one type cut to about equal expected cost, ten per participant, so the pool claims them one at a time and costly entities run alone. Groups time themselves (two clock reads per group, not per entity) and those times are each type's cost. Groups are recut only when a type's ideal size drifts 25% from its current one, and entities reordered only when the list is rebuilt or a type's costliest member becomes 25% costlier than that of one ahead of it, so a steady wave costs the server thread nothing per entity or per group. Profiles report each flat wave's longest group, when it started after the wave did (`longestGroupStart`), the groups still running when the caller ran out of work, and the average participants.

Which thread runs an entity is a matter of caches. Claimed in list order, any worker would tick any entity, so an entity ticked on one socket is often ticked on the other the next tick, and every cache line it wrote moves across with it. The wave therefore has homes (`WaveHomes`): each type's entities are cut into `workers + 1` equal slices of tick-list order, groups never cross a slice, and slice h of every type is home h, owned by participant h (the server thread is 0, worker i is i + 1). A participant drains its own home's groups of a type from the front, then takes other homes' groups of that type from the back, nearest home first, and only then starts the next type: types are still claimed costliest first. While membership is unchanged an entity stays in its home and on its thread. In a spread-out world at 36 workers that cuts remote-socket cache transfers about fivefold and the entity wave by about a quarter. Only a wave with every worker has homes: one capped by its longest tick (`flatParticipants`, a fight) is as long as that tick, runs slower with homes and is claimed in list order. `-Dvanadium.entityHomes=false` claims every wave in list order ([JVM properties](configuration#jvm-properties)).

All waves run their tasks through one call site in `WorkerPool`. A claim loop whose call site sees only entity groups gets the whole entity tick inlined by the JIT; every rare branch in it then deoptimizes the claim loop, which in measurements stayed interpreted for whole runs.

Overlapping ticks can also fail where serial ticks cannot: a value read after another tick removed it. Such failures do not repeat, so with `skipFailedEntityTicks` one failed tick is logged and its remainder skipped; the same entity failing three ticks running is a real bug and stops the server as vanilla does.

## Collections and publication

JCTools `NonBlockingHashMapLong` owns primitive-key storage and resizing for loaded full chunks, entity sections, column snapshots and byte-valued simulation/POI levels. Steady lookups take no shared monitor and do not box position keys. Byte values use the JVM cache.

Fastutil field types require small adapters. Where the field is typed by a fastutil interface the adapter extends fastutil's `Abstract*` base:

- `ConcurrentLongByteMap` adapts JCTools to `Long2ByteMap`, preserving default-return values and fastutil views. Its direct visitor uses primitive-key iteration.
- `ConcurrentLongObjectMap`, `ConcurrentIntObjectMap` and `ConcurrentLongLongMap` adapt JCTools `NonBlockingHashMapLong` (constructed with `opt_for_space = true` and `3×` expected-entry sizing via `nonBlockingSlots` to avoid premature resize storms): point reads and writes are lock-free and never box keys, while the compute and merge family serializes per-stripe on misses and updates so mapping functions stay atomic. Packed long keys go through Murmur3's bijective finalizer (`PackedPositionKeys`) so packed chunk and section coordinates do not cluster on the low hash bits; views decode original keys.
- `ListeningConcurrentLongObjectMap` replaces Lithium's listening POI section map: writes to one chunk column and their add/remove callbacks run under that column's stripe lock, reads take none, and entry views are read-only. It answers null for missing keys, not a default return value.

Where the field is typed by a concrete fastutil class, the adapter must subclass that class, and its inherited storage stays unused or is guarded:

- `ConcurrentLongSet` adapts `ConcurrentSkipListSet` to vanilla's `LongLinkedOpenHashSet` fields. Every superclass storage reader is overridden. Iteration is ascending, not insertion order.
- `ConcurrentLongObjectOpenHashMap` stands in for Lithium's `Long2ObjectOpenHashMap` column index (`SectionStorage.columns`, set reflectively by `LithiumCompat`), backed by a `ConcurrentLongObjectMap`. Every superclass storage reader is overridden.
- `SynchronizedLongReferenceOpenHashMap` keeps the superclass storage for Lithium's per-world chunk-section callback map and synchronizes its single-key operations; callers iterate under its monitor.

Spatial indexes remain domain logic rather than general-purpose containers. `AreaMap` paints nearby-player ranges and updates only their symmetric difference. `EntitySectionIndex` visits only columns intersecting an entity query, preserving vanilla's packed-key order. Each chunk column is one immutable entry (sorted Ys and their sections) replaced on change, so a column costs one lock-free map read and readers never see half of a write. Entity box queries pass their box, type and consumer down to each section instead of vanilla's per-query section lambda.

A section holding 24 or more entities also gets a `CrowdGrid` (2×4×2-block cells; built on the server thread after the level's ticks, when no box is being written; dropped below half that). It only prefilters small box queries such as pushing, which otherwise read every entity's box in the section while those entities move on other cores. Candidates still get vanilla's test on the live box and the caller's predicate, in the section list's order. Per-cell lists are immutable sorted arrays updated lock-free by CAS: single-cell queries are wait-free, two-cell queries validate the sequence counter and merge inline with zero scratch, and larger queries use `TickThread.crowdScratch`. Box writes from another tick to an entity in a crowded section wait for its owner, as position writes do; after an unprotected write (ownership timeout or cycle), grids are bypassed until rebuilt.

`NavigationIndex` filters invalidation candidates under a `ReentrantReadWriteLock`, tracks non-empty dirty stripes with a 64-bit `VarHandle` bitmask, and serves `ServerLevel.sendBlockUpdated` through a zero-allocation per-`TickThread` scratch iterator; dirty/custom/long-path cases retain a conservative fallback. It does not run pathfinding asynchronously. The level's path-type cache, read by every pathfinding mob, keeps each entry in one atomic long (`PathTypeSlots`: the position hash's high bits and the type), so lookups take no lock and stores allocate nothing. Ground pathfinding stays synchronous and vanilla-exact (`PathfindingFastPath`, `PathNavigationRegionMixin`, `PathfindingContextMixin`, `NodeEvaluatorMixin`, `WalkNodeEvaluatorMixin`, `NodeMixin`, `PathFinderMixin`): when Lithium's block-state cache is active and no Fabric `LandPathTypeRegistry` provider overrides a block, state path types are read directly from `PathNavigationRegion` without hitting the shared `PathTypeCache` or Fabric's empty-map lookup; neighbor hazard skips extend across chunk and section seams (with `LevelChunkSectionMixin` ensuring Lithium's block flags are initialized before its air-section counter checks `Blocks.AIR`); `WalkNodeEvaluator` keeps a padded `WalkScratch` directly on `TickThread.walkScratch` with generation-stamped spatial caches, a lazy per-search malus table, allocation-free `getPathTypeOfMob`, and a primitive open-addressed `Node` table + pool active during `PathFinder.findPath` (when `!captureDebug`) that clones only the winning reconstructed path before `done()`.

Entity inside-block and line-of-sight hot paths (`InsideBlockFastPath`, `LineOfSightFastPath`) replace per-call `LongOpenHashSet`, `Vec3`, `ClipContext`, `EntityCollisionContext`, and `BlockHitResult` allocations with primitive-register traversals, local chunk/section caching, air skipping, bit-exact `clipsFullCube` tests, and a reusable padded open-addressed visited table on `TickThread.insideBlockScratch`.

## World access

- `ParallelChunkCache` serves published loaded full chunks from its concurrent map for _every_ `ChunkStatus` (`FULL`, `STRUCTURE_STARTS`, `STRUCTURE_REFERENCES`, `BIOMES`), eliminating C2ME `ItemHolder` lock contention during spawning. `LevelChunk.setLoaded` publishes/removes entries; a private publication monitor protects identity-conditional removal so an old unload cannot remove a replacement. Reads stay outside that monitor. During `Stage.SPAWNING`, a short-lived wave-scoped proto-chunk cache (`beginStructureWave` / `endStructureWave`) also caches border proto-chunks outside `loadedChunks` without retaining chunks across unloads.
- Misses/status requests stay with vanilla/C2ME. On the server thread they run under per-position reentrant load locks, so a load started inside another (a load callback asking for a neighbour) takes its lock in place; FULL publication is rechecked after acquiring the load lock. Never publish null or non-FULL results. `ServerChunkCacheMixin` skips vanilla's four-entry parallel-array cache (`storeInCache` and post-construction `clearCache`), leaving those arrays immutable (`INVALID_CHUNK_POS`/null) so misses never race on parallel-array reads or take a cache monitor. Minecraft's own background workers bounce synchronous loading to the server thread.
- Only the server thread takes load locks (`ChunkLoadLocks`). Only it can finish a miss (C2ME adds new holders, ticket updates and FULL promotion there), so a lock held by any other thread would be held while waiting for the server thread, and the server thread asking for the same chunk would wait for it in turn. Other threads outside waves run vanilla/C2ME without a lock.
- Vanadium workers use a chunk where they stand only if C2ME has already completed the requested status (or, without loading, no holder exists). Otherwise a task run through `WorkerPool.runDeferrable` unwinds with `ServerThreadRequired` and reruns on the server thread after the wave. Any other task hands the lookup to the wave's caller, the server thread, with `WorkerPool.callOnWaveCaller` and waits holding no load lock (a rate-limited warning names the caller): the caller serves it between its own claims and while it waits for the wave's tail, outside any task of its own, so the wait ends when the caller's current task does. Region schedulers also serve these requests between regions and while waiting for conflicts or dependencies, outside any region claim. Mods' load callbacks still wait for the end of the wave. A worker must not hold a lock that the server thread's tasks or chunk loading can wait for while it makes such a lookup; a wait longer than 10 s (`vanadium.callerRequestStallSeconds`) logs the stalled caller.
- The server thread defers deferrable tasks the same way while helpers run: it could load, but the chunk-system work (status changes, entity and POI loading, mods' load callbacks) would then overlap the workers. `WorkerPool.runAfterParallelWave` queues other such server-thread work until the wave's tasks have all finished. Spawning is deferrable: it prechecks the chunk's referenced structure starts, so the usual deferral (joins and exploration) happens before any spawn attempt.
- `ChunkLoadLocks` reserves entries atomically against eviction. Unlock before dropping a reservation; maintenance must not evict a held or pending lock.
- Per-holder synchronization protects chunk block/light updates. Dirty notifications queue to the server thread; workers never mutate the ordered eager-save set or wait for disk IO.
- Section storage (POI) gets its concurrent map and dirty set when constructed. Callers loading the same column wait for its first loader, which reads off the server thread; vanilla let a second caller read the column before its sections were stored. POI sections synchronize their methods, and their per-type map and sets are concurrent: vanilla's record streams and Lithium's iterators are consumed after the section's lock is released, while other regions add POI. Records and the village distance graph follow [POI locking](#poi-locking).
- Saved-data cache hits are concurrent; misses and snapshot creation synchronize separately from asynchronous disk writes. Never hold that monitor across `saveAndJoin` or close waits.
- Immutable path-type entries prevent torn key/type reads. POI and simulation levels use the byte-map adapter. Per-thread random streams (cached on `TickThread`) avoid a shared world-random monitor, `LegacyRandomSourceMixin` advances seeds with a lock-free compare-and-set loop (outside `SyncAllMixin`), `Level.randValue` is per-thread via `VanadiumMixinPlugin`, and neighbor updates use per-thread `CollectingNeighborUpdater` delegates.

Isolation does not protect arbitrary cross-region interactions. Shared world monitors and collection contracts are still required.

### POI locking

Villagers in the flat entity wave claim, release and search POI from any thread, and each ticket change re-evaluates its section's village-centre level in the distance graph (`PoiManager.DistanceTracker`). The monitors, outermost first:

Records hold no monitor (`PoiRecordMixin`): tickets change by compare-and-set and are read as volatile, and the section's dirty callback runs after the swap. A raw `acquireTicket` therefore holds nothing, a claim (`PoiClaims`, below) and a release hold their section, a load holds its stripe, and each takes the graph last.

Vanilla computes the level it publishes before taking the graph's monitor, so two threads changing one section could publish in the opposite order to their reads and leave a stale village centre (or miss one). `PoiManagerMixin` re-reads the level inside the monitor: the last update for a section follows every change made before it, and the graph converges on the current POI state.

Claims honour the ticket they took, on a record that is still installed. Vanilla returns a claim's position whether or not its ticket was still free, so two villagers picking the last ticket of one record could both keep it; and it finds its candidate before it claims (Lithium's searches collect candidates into a list), so the record may meanwhile have been removed by a block change, dropped by a section refresh or detached by a column unload, and a ticket taken on it is saved nowhere. Both claims commit through `PoiClaims`: under the section's monitor, the storage map (read without loading) must still hold that section and the section that record at its position; then the ticket is taken by compare-and-set and the dirty callback runs (section, then the terminal graph). Removal, refresh and `pack` are synchronized section methods, so each is ordered wholly before or after a claim; no caller predicate and no load runs under that monitor. `take` (breeding beds, and job sites when Lithium's `ai.poi.tasks` is off) skips a candidate that fails the commit and searches on, as if that change had come first (`PoiManagerMixin`); Lithium's exact-position `takeAt` returns empty (`PoiTakeAtMixin`, one optional hook that `VanadiumMixinPlugin` requires wherever `takeAt` exists). `AcquirePoi` stores the job-site memory, sends its event, clears its retry cache and updates debug info only after a claim of its target (`AcquirePoiMixin`); a lost claim changes nothing, and the next scheduled attempt searches again. Each ticket therefore goes to one claimant, on the record that is saved, and only a claimant that took one remembers the POI. `PoiRecord.acquireTicket` itself stays a plain compare-and-set for other callers.

C2ME's POI unloading (`chunkSystem.allowPOIUnloading`, on by default) flushes a column and removes its sections when its chunk downgrades, on the server thread's executor, holding no POI monitor and telling nobody. That executor also runs while the server thread waits inside a parallel wave, where workers may be claiming in the column; and a village centre in a removed column drops out of the graph at the next nearby update, where vanilla (which never unloads POI) keeps it while it is occupied. `PoiUnloadMixin` adds two vetoes to C2ME's merged `shouldUnloadPoi`, never overriding its own refusal: on a parallel wave's caller (or a worker), and for a column with a village centre in any installed section (the graph's only sources; every vanilla type with tickets is a village type, so every claimed ticket is covered). An unload therefore runs only when no other thread claims, and removes no source: no level in the graph changes, and nothing is invalidated. A ticket claimed before the unload is in the flushed data and reloads with the column. On the server thread itself, a candidate found before an unload pumped by its own search fails the commit. A vetoed column stays loaded, as in vanilla, until C2ME asks again on a later downgrade of that chunk; the request is not queued or replayed, since nothing records whether the chunk was loaded again in between. The hook is optional (absent without C2ME's chunk-system rewrite) and `VanadiumMixinPlugin` requires it wherever the method exists.

Saving reads ticket counts after the dirty mark: a ticket changes before its column is marked dirty (concurrent set), and a write removes the mark before packing, so it either includes the change or the column stays marked for a later write.

**Limits:**

- Columns are retained more than with C2ME alone: those whose chunks downgrade during a parallel wave, and those holding a village centre, stay loaded as vanilla keeps every column, until a later downgrade finds them eligible. Memory then grows with chunks unloaded mid-wave; a village centre's column is bounded by the villages, as in vanilla.
- The guarantees cover vanilla's and the pinned Lithium's and C2ME's paths. A mod that calls `acquireTicket` itself skips the installed check, and one that removes POI sections by other means is not vetoed. A ticketed POI type outside the village tag (a mod's, or a datapack's edit of the tag) is not a village centre, so its column may unload outside waves; its tickets are flushed first and reload with it. Outside waves the unload is ordered against claims and section creation only because no other thread does either then; a mod doing so off-thread is not covered.
- A claim of a record that a concurrent block change removes is ordered by the section's monitor: before the removal, the ticket goes with the record and vanilla's job-site validation drops the memory; after it, the claim fails.
- Lithium's queries run callers' predicates under a section monitor. Vanilla's and Lithium's predicates take no POI monitor; a mod predicate that took another section's monitor, or waited for the server thread, could still stall that section.

## Preparation and networking

### Spawning

Spawn preparation replaces vanilla's entity iterator with scoped per-thread slices, retaining C2ME filtering and vanilla's environment-aware costs. Workers count independent slices while sharing `LocalMobCapCalculator`'s pre-sized concurrent `playersNearChunk` cache across jobs; the caller reduces counts, player caps and charges in input order. Overrides clear in `finally`. Spawn attempts remain a separate stage, with lock-free mob-category reads through `ConcurrentMobCategoryCounts` on `NaturalSpawner.SpawnState` and `LocalMobCapCalculator`.

With `parallelSpawning = false` and parallel chunk ticks, `tickSpawningChunk` runs as in vanilla: each visited chunk's thunder runs inline at its original call, before that chunk's eligibility checks and spawn attempt, and the attempt follows inline, in vanilla's shuffled order. Nothing is queued in the spawning stage, so its wave is empty; the stage barriers before the block-ticking pass stay. `ChunkStage` lists what runs inline and what is queued for every combination of `enabled`, `parallelChunkTicks` and `parallelSpawning`.

The slices of Lithium's section iteration are ranges of the entity section index's column slots: every column keeps a slot in a dense array (a removed column's slot takes the last one), so the caller cuts the level into ranges without reading a column, and each worker walks its own columns. A scan records each column's entity count, and the next tick's cut is weighted by them (plus a fixed cost per column), so crowded columns get ranges of their own; one column is never split. Ranges are valid while no section is created or removed, which holds during the counting wave.

Vanilla counts every tick even with `spawn_mobs` false, though only `getLastSpawnState` (debug screen, `/perf` report, mods) can then see the result. `SpawnCounts` skips that count on dedicated servers until something reads the state: the tick stores an empty placeholder with vanilla's spawnable chunk count, and the first read on the server thread outside a wave counts then (from the entities as they are at that point), stores it, and makes every later tick count; a read elsewhere returns null (as before the first tick) and turns counting on from the next tick. Integrated servers, `enabled = false` and `parallelSpawning = false` always count.

### Spawning participants

`-Dvanadium.spawnParticipants=N` (experimental, default `auto`; [JVM properties](configuration#jvm-properties)) bounds spawning waves at N threads including the server thread, for measuring the shared spawn-state behaviour against fewer threads. It is an upper bound, not an occupancy: a wave is offered the smaller of the scheduler's estimate and N (what JFR `WaveEvent` and tick profiles record), a one-region wave still runs inline, and offered workers that find no claimable region stay idle. With parallel spawning the spawning wave also carries the thunder of ticking chunks, which the bound covers too. `1` runs the regions inline on the server thread in plan order, where blocking chunk lookups need no deferral. Learned estimates, the region plan, the spawn count (`SPAWN_COUNTS`) and every other stage are unchanged.

### Tracking and chunk packets

Tracking owns reusable per-player diff rows and stable tracker slots through both barriers. A level without players skips the move scan; moves are detected by position identity, so the first scan after a join catches up before the first diff. Workers prepare flags without callbacks; one subsequent task per tracker applies changes in player order. Chunk packet preparation runs between simulation ticks, keeps selected batch order and vanilla packet contents, and falls back inline for small batches.

## C2ME and Lithium

C2ME owns generation, holder promotion and ticket scheduling. It is required. Two named thread-detection mixins are cancelled by the Java bootstrap integration (`compat/C2ME.java`). Mods that also rewrite ticking or the chunk lookup path (Async, DimThread, MCMT, Moonrise, ServerCore, VMP) are declared incompatible in `fabric.mod.json`.

Lithium is required; Vanadium compiles against the pinned 0.26.3. `fabric.mod.json` disables, through `lithium:options`, the Lithium options whose job Vanadium does with thread-safe structures: chunk access, entity class filtering and per-type lists, entity retrieval, the entity tick list, navigation tracking and the profiler. It also disables `alloc.chunk_random`, which shares one mutable position per world between parallel random ticks, and the experimental suffocation cache (`experimental.entity.block_caching.suffocation`, off by default): Vanadium's `isInWall` is an allocation-free loop with vanilla's checks. The rest stay enabled. The Lithium state that parallel stages share in the pinned version is made safe as follows; a later Lithium may add state these points do not cover:

- Entity class groups (`ClassGroupFilterableList`) come from Vanadium's copy-on-write `ClassInstanceMultiMap`; `compat.Lithium` cancels Lithium's single-threaded lists. Lithium's entity collision and projectile-collision shortcuts depend on them and stay on. Its cramming filter (`entity.collisions.unpushable_cramming`) is disabled: entities of any thread change a section's masked list as their feet block changes, and it would bypass the crowded-section grid.
- POI section storage keeps Lithium's per-column index on a concurrent listening map; writes to one column and their index updates hold a column stripe lock, and reads take none. An unsupported storage layout stops initialization instead of continuing with an unsafe shared map.
- Game-event dispatch reads per-chunk listener maps without the chunk's monitor, so those maps are concurrent and removal takes the monitor that creation already held. The per-world dispatcher storage takes a write lock for its rare updates; reads are optimistic and retry under a read lock only if a write overlapped them.
- Chunk load/unload callbacks (`ChunkStatusTracker`) run on the server thread, which can change chunk status mid-wave; they are queued until the wave's tasks finish, before the chunk unloads.
- Entity movement tracking (hoppers waiting for items to move) keeps per-section waiting lists that item and container entities empty on every move. In sections a tracker registered with, those moves and every list or registration change hold one lock; elsewhere moves only stamp the section's move time, without it.
- Tracker interning, the world-border listener registry (every block-entity ticker re-registers after a border change) and chunk-section callback registration (hoppers) are synchronized; all are rare.

Users may still disable Lithium options in `config/lithium.properties`; injections into methods those options add are optional (`require = 0`), and section storage falls back to Vanadium's concurrent map. `MixinTargetsTest` checks bindings against the pinned Lithium jar, and every live run includes Lithium with its default options plus the ones `fabric.mod.json` disables; other option combinations are not live-tested. The manifest accepts later C2ME and Lithium versions, but only the pins are built against and tested.
