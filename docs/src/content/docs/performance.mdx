## Worker count

Uncapped TPS by `workers`, against the same server with Lithium but without Vanadium and C2ME ("Lithium alone", one tick thread). Means of four samples with their range; [all 132 samples (CSV)](https://github.com/synsejse/Vanadium/blob/dev/docs/benchmarks/worker-scaling-26.3.csv).

- At the default 36 workers the three worlds run 14.4×, 9.1× and 10.7× faster than Lithium alone. Two workers already give 2.7–3.1×, eight give 5.5–6.9×.
- Throughput levels off between 24 and 48 workers. Each world peaks at a different count, but the default measured within 2% of every peak, inside the peak's sample range.
- One worker per logical processor (72 here) leaves nothing for the server thread, C2ME and the garbage collector, and ran up to 43% below the best setting.
- Combat keeps its throughput with more workers: its entity wave uses no more threads than its longest tick leaves work for (about 30 here), and the rest stay parked.

The best count depends on the machine and the world: start from the default and compare a few values with `/vanadium benchmark`.

**Method.** Measured 2026-11-14 at `e29ec28`, `isolation = 2`, no extra JVM flags. One fresh server JVM per point and pass, running Lithium alone, an ascending pass over the worker counts, a descending pass, then Lithium alone again. Each JVM runs two `/tick sprint` windows of 2,000 ticks for the spread-out world, 15,000 for the crowded base and 2,500 for combat. The crowded base's second window is always 9–22% faster than its first, which is what widens its ranges. Compare numbers within this table, not with other measurements: Lithium alone also moves between sweeps.

### Default worker count

`workers = 0` gives `min(physical cores, logical processors − 1)`: every core gets a worker, and the server thread, which joins every wave, gets the remaining logical processor (an SMT sibling, or a core without SMT). On the test machine 32, 35 and 36 workers measured within noise of each other. Small machines, emulated with CPU affinity on the same host:

| CPUs                                 |     Workers |       Spread out |        Combat |
| ------------------------------------ | ----------: | ---------------: | ------------: |
| 4 cores × 2 threads (CPUs 0–7)       |           3 | 87.5 (73.1–96.2) | 123 (117–131) |
|                                      | 4 (default) | 93.9 (90.8–95.8) | 124 (119–129) |
|                                      |           5 | 93.0 (83.2–98.1) | 128 (119–136) |
| 4 cores × 1 thread (CPUs 0, 2, 4, 6) | 3 (default) | 84.6 (75.2–90.9) | 117 (110–124) |
|                                      |           4 | 78.5 (74.9–80.5) |  101 (96–106) |

Without SMT, one worker per core plus the server thread oversubscribes the cores: 3 workers beat 4 by 8% and 16%. With SMT the server thread fits on a sibling. Measured 2026-11-14 at `a74931b`, four rounds with the order of the counts rotated each round.

## Recommended JVM flags

On Linux with more than one NUMA node (`lscpu` shows the node count), and with memory to dedicate to the server:

```sh title="Linux multi-NUMA JVM flags"
java -Xms4G -Xmx4G -XX:+UseNUMA -XX:+UseTransparentHugePages -XX:+AlwaysPreTouch \
     -XX:+UseCompactObjectHeaders -jar server.jar nogui
```

Use the same value for `-Xms` and `-Xmx`, sized to what the machine can give the server, and leave room outside the heap for the JVM, mods and operating system. These measurements used 4 GiB; that is the benchmark heap, not a sizing recommendation for every modpack.

| Combat       |       295 (285–313) |                291 (271–303), −1% |       <span class="gain">329 (319–345), +12%</span> |        314 (308–326), +7% |

- All four flags together beat no flags in every round of every workload, and beat `UseNUMA` alone in 22 of 24 rounds.
- `-XX:+UseNUMA` carries most of the gain: the collector hands each thread new objects from its own node's memory, and the same worker ticks the same entities every tick.
- At normal 20 TPS (spread-out world) the average tick fell from 6.98 ms to 5.15 ms and p99 from 22.7 to 14.5 ms.
- **The whole heap is committed at start:** `-XX:+AlwaysPreTouch` makes a 4 GiB heap resident at once and adds about 4 s to startup.
- **Huge pages need kernel consent:** `/sys/kernel/mm/transparent_hugepage/enabled` must be `madvise` or `always`.
- **`UseNUMA` needs `libnuma.so.1`** on `LD_LIBRARY_PATH`; `-Xlog:gc+init` prints `NUMA Support: Enabled` when active. Omit it on single-node hosts.
- Drop `-XX:+AlwaysPreTouch` and `-XX:+UseTransparentHugePages` if memory is shared with other services.

Measured 2026-11-14 at `e29ec28`, `workers = 36`, `isolation = 2`, G1, `-Xms4G -Xmx4G`.

## Idle workers at 20 TPS

At the normal 20 TPS the threads sit idle for most of each 50 ms, and on some machines a tick after a long sleep runs much slower than the same tick under `/tick sprint`. The `idleWorkers` modes trade idle CPU for that wake-up cost. Tick work by mode (`/vanadium profile`, 1,201 ticks over 60 s, 4,096 zombies over 1,024 chunks, 24 workers):

| Mode             | Runs | Tick avg (ms) |     p95 |       p99 | Worker CPU | Server thread CPU |
| ---------------- | ---: | ------------: | ------: | --------: | ---------: | ----------------: |
| `lean` (default) |    6 |     6.26–6.80 | 8.3–9.4 | 13.5–18.3 |     11–12% |            12–13% |
| `balanced`       |    4 |     6.06–6.53 | 7.5–8.8 | 10.9–16.3 |     11–15% |               98% |
| `hot`            |    5 |     5.50–5.89 | 7.2–7.8 |  9.4–15.8 |        99% |            11–99% |

On this host the difference depended on its power state: in a slower state the same `lean` ticks took 12.0–12.2 ms against 6.0–6.6 ms for `hot`, while in the state above the three modes are close. `lean` is the default because it costs nothing where spinning does not help. If `/vanadium profile` at 20 TPS shows ticks much slower than a sprint, try `balanced`, then `hot`. Measured 2026-11-12, before vCPU pinning.

## Environment and limits

Dual Xeon E5-2699 v3 (2.3 GHz; about 3.3 GHz with one busy core, 2.7 GHz with all busy) running Proxmox. The benchmarks run in a KVM guest with 72 vCPUs (two sockets × 18 cores × two threads), each pinned 1:1 to a host CPU, two NUMA nodes bound to the host's, 15 GiB of memory, NixOS, transparent huge pages `madvise`. Other VMs share the host; guest steal time stays below 1%. OpenJDK 25.0.4.1, fixed 4 GiB G1 heap and no other JVM flags unless a section says so. Minecraft 26.3, Fabric Loader 0.20.1, Fabric API 0.165.2+26.3, Fabric Language Kotlin 1.14.2, Cloth Config 26.3.159, Lithium 0.26.3, C2ME 0.4.2-alpha.0.116 with global parallelism four.

Sprint worlds are fresh seed-12345 flat worlds with the mob area force-loaded, view and simulation distance four, no players, and spawning, time and weather cycles and mob griefing off. Mobs are summoned persistent and invulnerable (in the combat arena they get Resistance instead, so they fight), settle for 30 seconds, then two `/tick sprint` windows run back to back in one JVM.

- TPS here is uncapped **processing capacity**, not a faster game: a normal server still runs at 20 TPS and uses the headroom to stay there under load.
- A dedicated server with `spawn_mobs` false skips the mob count, so these worlds leave out a cost a server with spawning on still pays.
- Two windows in one JVM are not independent replication, and no tail-latency improvement is claimed beyond the 20-TPS tables above.
